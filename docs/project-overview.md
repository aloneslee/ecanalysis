# 项目维护与上手说明

这份文档面向第一次接触 `ecanalysis` 的开发者，帮助你快速理解项目目标、后续开发方向，以及维护时应该关注哪些地方。

## 1. 项目要解决什么问题

`ecanalysis` 想做的是一个金融分析服务内核。

它会从多个来源收集信息，比如财报、行情 K 线、公告、新闻、X 和 Reddit 等社交平台内容，然后把这些信息整理成一份结构化的股票分析报告。

简单说，项目核心链路是：

```text
数据输入 -> 数据清洗 -> 分析处理 -> 报告生成 -> 对外提供结果
```

## 2. 推荐的最小开发闭环

初版不要一次性接入所有数据源，建议先做一个最小闭环：

1. 选择一个股票代码作为输入
2. 接入一个稳定的数据源
3. 解析一小部分关键数据
4. 生成一份简单报告
5. 把报告结果通过 API 或命令入口输出

这样可以更快验证项目方向，也方便后续逐步替换或增加数据源。

## 3. 推荐目录职责

后续创建代码时，可以优先参考下面的职责划分：

```text
app/api/
```

放对外接口，比如 HTTP API、任务触发接口、报告查询接口。

```text
app/core/
```

放项目通用能力，比如配置读取、日志初始化、异常类型、应用启动逻辑。

```text
app/data_sources/
```

放外部数据源接入逻辑。比如行情接口、财报接口、新闻接口、社交平台接口。

```text
app/analyzers/
```

放分析逻辑。比如财务指标分析、行情趋势分析、社交情绪分析、风险识别。

```text
app/reports/
```

放报告生成逻辑。这里负责把分析结果整理成 Markdown、HTML、JSON 或其他格式。

```text
app/schemas/
```

放统一的数据结构定义，避免不同模块之间传递结构混乱的数据。

```text
tests/
```

放测试代码。后续每个核心分析模块都应该有对应测试，尤其是数据清洗和报告生成部分。

## 4. 开发环境建议

居千本地是 Windows 环境，项目开发时建议使用虚拟环境。

推荐优先使用：

```text
.venv
```

或者：

```text
venv
```

后续如果添加依赖文件，可以根据项目选择：

- `requirements.txt`：简单直接，适合初期项目
- `pyproject.toml`：更现代，适合后续规范化管理

初版更推荐先使用 `requirements.txt`，等项目结构稳定后再决定是否迁移到 `pyproject.toml`。

## 5. 数据源维护原则

金融数据源经常会遇到这些问题：

- 接口字段变化
- 请求频率限制
- 数据延迟
- 数据缺失
- 不同来源口径不一致

所以每个数据源模块后续都应该尽量做到：

- 明确记录数据来源
- 明确记录更新时间
- 对缺失字段做兼容处理
- 不在采集层直接写复杂分析逻辑
- 失败时返回清晰错误，方便排查

## 6. 报告生成原则

分析报告应该尽量做到“有结论，也有依据”。

推荐报告至少包含：

- 输入股票代码
- 报告生成时间
- 使用的数据来源
- 财务摘要
- 行情摘要
- 信息面摘要
- 社交平台观点摘要
- 风险提示
- 分析结论

任何偏判断性的内容，都应该尽量说明依据，避免只给出无法追踪的结论。

## 7. 后续优先级建议

建议按这个顺序推进：

1. 搭建 Python 项目骨架
2. 增加配置与日志模块
3. 定义报告数据结构
4. 实现一个最小数据源接入
5. 生成第一版 Markdown 报告
6. 再考虑 API 服务和更多数据源

这样可以让项目一直保持可运行、可验证、可维护。

## 8. 注意事项

本项目涉及金融分析，维护时需要特别注意：

- 不要把分析结果包装成确定收益承诺
- 不要隐藏数据来源
- 不要忽略数据延迟和缺失
- 不要把社交平台情绪当成唯一依据
- 不要在没有验证的情况下扩大功能范围

项目输出内容只适合作为研究辅助，不构成投资建议。

## 9. 版本控制忽略项

项目根目录下的 `.gitignore` 会忽略本地仓库、工作助手相关目录，以及只在本地查看的文档草稿目录：

- `.git/`：Git 本地仓库元数据，不应该提交到远程仓库
- `.codex/`：本地 Codex 工作配置和上下文，不应该暴露到 GitHub
- `.agents/`：本地助手配置和上下文，不应该暴露到 GitHub
- `docs/local/`：本地临时文档草稿，不提交到 GitHub
- `docs/private/`：本地私有文档草稿，不提交到 GitHub

后续如果新增密钥、缓存、虚拟环境或本地生成文件，也应该优先加入 `.gitignore`，避免误提交。
